# 9. Polymarket 검증 결과와 "사용자 기준 반영" 설계

작성 2026-11-24

## 1. Polymarket 검증: 실제 돈의 시장에서도 마감 직전 손실이 나는가

### 대상과 방법
- **대상:** 하루 단위로 기준가가 여러 개인 시장. HSK 예측시장("NVDA ≥ $180/185/190")과 같은 구조다.
  - `bitcoin-above-on-{날짜}` 2,132개, `ethereum-above-on-{날짜}` 1,242개, `nvda-close-above-on-{날짜}` 395개
  - 기간 2026-08-01 ~ 11-22, 정산된 이항 시장 3,769개, 시장 거래액 합계 3.70억 달러
- **조회:** Gamma API(`/events?slug=`)로 시장과 정산 결과를 받았다. Data API v2(`/v2/trades?condition=`, `taker_only` 기본값 true)로 테이커 체결 2,898,355건, 지갑 154,621개를 받았다.
- **계산:** 테이커가 실제로 갖게 된 쪽의 가격을 지불가로, 정산 결과를 수령액으로 놓았다. 기준 시각은 시장의 `endDate`(결과 확정 시각)다.
- **정제:** 같은 시장·같은 1분 안의 다른 체결과 가격이 0.1 넘게 다른 체결(전체의 18.6%)은 뺐다. 예: BTC가 82,800달러일 때 "82,000 위" YES가 0.002에 체결된 기록. 묶음 시장의 전환 거래로 보인다. 1달러 미만 체결도 뺐다. 남은 체결은 1,490,341건, 1.90억 달러다.

### 결과 (정제 후)
| 결과 확정까지 | 체결 | 테이커 지불 | 테이커 수익률 | 가격 중앙값 | 적중률 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 0~1시간 | 57,116 | 1,440만 달러 | **+0.8%** | 0.84 | 64.9% |
| 1~6시간 | 223,300 | 4,390만 달러 | **+0.8%** | 0.80 | 64.6% |
| 6~24시간 | 676,669 | 7,992만 달러 | −0.8% | 0.65 | 60.6% |
| 24~72시간 | 370,896 | 3,742만 달러 | −2.4% | 0.62 | 57.7% |
| 72시간 이상 | 160,174 | 1,356만 달러 | −0.6% | 0.57 | 54.8% |

마감 24시간 안의 "거의 확실해 보이는 쪽"(가격 0.85~0.99)은 수익률 +0.6%와 −0.1%로, **가격만큼 정확히 맞았다.** 정제하지 않은 원자료에서도 마감 직전 구간의 수익률은 +0.8~0.9%였다. 결론은 정제 방식에 따라 바뀌지 않는다.

### 해석
| | HSK 예측시장 (이벤트 자금) | Polymarket (실제 돈) |
| --- | --- | --- |
| 마감 1시간 이내 테이커 | −99.2% | +0.8% |
| 마감 1~6시간 | −62.2% | +0.8% |
| 가격과 적중률 | 0.85~0.89에 사서 1~37% 적중 | 가격만큼 적중 |

- **"마감 직전에 확실해 보이는 쪽을 사면 진다"는 문제는 실제 돈의 큰 시장에는 없다.** HSK 예측시장에서만 나타났다.
- HSK 쪽 원인은 이벤트 자금이라 대충 사는 행동, 또는 그 플랫폼의 가격이 현실을 늦게 따라가는 구조로 보인다. 어느 쪽인지는 이벤트 제목 없이는 가릴 수 없다.
- **판정: A′(예측시장 거래 에이전트)의 "실제 돈의 페인"은 확인되지 않았다.** 앞서 정한 대로 A′는 보류하고, 2순위로 넘어간다.

## 2. 2순위로 이동: 이슈 기반 HSK 분할 매도 에이전트

| 항목 | 내용 |
| --- | --- |
| 타겟 사용자 | 큰 물량의 HSK를 가진 트레저리. 이더리움 멀티시그 3개(7,583만 / 7,468만 / 3,709만 HSK), 체인 위 운영 주소 `0x8fed…95e` |
| 상황 | 운영비·투자·리밸런싱 때문에 HSK 일부를 스테이블로 바꿔야 한다. 시장이 얇아 한 번에 팔면 손해가 크다(HSKSwap 100만 HSK −16%) |
| 결정 | 언제, 얼마나, 어디서(HSKSwap인지 거래소인지) 팔지, 그리고 어떤 소식이 나오면 멈추거나 앞당길지 |
| 기존 방법 | 담당자가 직접 나눠 팔거나 장외 거래 데스크에 맡긴다 |
| **남은 약점** | HSK는 외부 뉴스에 약하게 반응한다(BTC와의 일 단위 상관 0.36, Base 협력 발표일 변화 없음). 트레저리의 매도 의사를 확인하지 못했다. 지난 주제(분할 매도)와 겹친다(사용자 요청으로 허용) |

## 3. "자동화에서 그치지 않고 사용자 기준이 반영되는" 설계

자동화만 하는 봇은 "규칙대로 실행"에서 끝난다. 여기서는 **사용자가 자기 판단 기준을 정하고, 에이전트는 그 기준에 맞춰 판단하고, 기준과 결과를 맞춰 보며 기준을 고치도록 돕는다.** 아래는 이슈 기반 분할 매도에 맞춘 설계이고, 같은 틀을 다른 후보에도 쓸 수 있다.

### 3-1. 사용자가 정하는 기준 (설정 화면)
| 기준 | 예시 | 계약이 강제하나 |
| --- | --- | --- |
| 목표 | 30일 안에 HSK 500만 개를 USDT로 | 총량, 만료 ○ |
| 가격 하한 | 0.075 아래로는 팔지 않음 | ○ (최소 수령액) |
| 한 번에 감수할 손해 | 견적 손해 0.5% 이하 | ○ |
| 소식에 대한 태도 | "규제 악재면 매도 앞당김, 제휴 호재면 멈춤, BTC −5% 이상이면 하루 멈춤" | 에이전트가 따름 |
| 사람 승인 기준 | 한 번에 20만 HSK 넘으면 담당자 승인 | ○ (승인 서명 필요) |
| 성향 | 빨리 끝내기 ↔ 좋은 가격 기다리기 | 에이전트가 따름 |
| (보조) KYC 등급 | 등급별 위임 한도 | ○ |

### 3-2. 에이전트가 하는 일
1. **기준을 문장에서 규칙으로 바꾼다.** 사용자가 쓴 말("규제 악재면 앞당김")을 판단 규칙으로 옮기고, 사용자에게 다시 보여 확인받는다.
2. **매 결정마다 어느 기준 때문에 그렇게 했는지 적는다.** 예: "BTC −5.6% → '하루 멈춤' 기준 적용 → 오늘 매도 0".
3. **기준끼리 부딪히면 묻는다.** 예: 마감은 다가오는데 가격이 하한 근처라면, 목표와 가격 하한 중 무엇을 우선할지 사용자에게 묻는다.
4. **결과와 기준을 맞춰 본다.** 지난 2주 동안 "제휴 호재면 멈춤" 기준이 실제로 이득이었는지 보여 주고, 기준을 바꿀지 제안한다. 바꾸는 것은 사용자가 한다.
5. **사용자의 승인·거절에서 배운다.** 담당자가 반복해서 거절하는 유형의 제안(예: 주말 매도)을 기록하고, 이것을 기준으로 추가할지 묻는다.

### 3-3. 이 설계가 "자동화"와 다른 점
| | 단순 자동화 (TWAP 봇 등) | 이번 설계 |
| --- | --- | --- |
| 기준 | 개발자가 정한 고정 규칙 | **사용자가 자기 말로 정함** |
| 설명 | 없음 | 결정마다 적용된 기준을 기록 |
| 충돌 | 먼저 정한 규칙이 이김 | 사용자에게 우선순위를 물음 |
| 개선 | 없음 | 기준과 결과를 비교해 수정을 제안 |
| 계약 | 실행만 | 사용자 기준 중 돈과 관련된 것(하한, 한도, 승인)을 강제 |

## 4. 다음 할 일
1. **HSK가 크게 움직인 날의 원인 찾기.** 6/2 −6.4%, 6/5 −10.1%, 11/20 −3.4% 등. 이 원인이 소식(해제 물량, 상장, 규제, BTC)과 연결되는지 본다. 연결되면 "소식에 대한 태도" 기준이 실제로 쓸모 있다는 근거가 된다.
2. **트레저리 주소의 실제 매도 흔적.** 이더리움 멀티시그 3개에서 거래소로 HSK를 보낸 기록이 있는지 본다. 있으면 "언제, 얼마나 팔았는지"가 타겟 사용자의 실제 결정 기록이 된다.
